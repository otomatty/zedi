# PoC: hono/jsx/dom + Better Auth + D1 による Zedi

Zedi を一から作り直す前提で、次の 5 点を確かめる PoC です。既存データとの互換は考慮していません。対象は Web アプリ（PWA）のみで、Tauri のデスクトップ版は要件から外しました。

- **フロントからバックエンドまで Hono だけ**で組めるか
- 認証（Better Auth）と D1 を入れた状態で、Cloudflare に一本化して成り立つか
- 重い画面（大量の一覧、長い文書の共同編集、AI 応答のストリーミング）でも性能が出るか
- Markdown のストリーミング表示と、大きな文書の編集をどう設計すべきか
- Web アプリがオフラインでも使えて（一覧・編集・ページ作成）、あとで同期できるか

## 構成

Cloudflare Worker 1 本ですべてを配信します（`wrangler.jsonc`）。フロントと API が同じオリジンなので、CORS の設定やサードパーティ Cookie は不要です。

| パス                     | 中身                                                                                          | 技術                                                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`                      | 公開ページ（JS なし）                                                                         | Worker 上で `hono/jsx` によるサーバー描画（`src/worker/landing.tsx`）                                                                             |
| `/api/auth/*`            | 認証                                                                                          | Better Auth（`better-auth/minimal` + Drizzle アダプタ + D1）。マジックリンクでサインイン。Google は資格情報を設定したときだけ有効                 |
| `/api/*`                 | ページ一覧・作成・詳細、共有メンバー、全文検索、疑似 AI ストリーミング（テキスト / Markdown） | Hono（`src/worker/app.tsx`）+ D1。全ルートでセッション必須、ノート単位の認可                                                                      |
| `/parties/page-room/:id` | 共同編集                                                                                      | ページごとの Durable Object（`PageRoom`）。接続時にセッションとページの権限を確認し、閲覧者は書き込み不可。保存時に本文のテキストを D1 に書き戻す |
| `/sw.js`                 | Service Worker（オフライン）                                                                  | `src/client/sw/` からビルド。後述の「オフライン（PWA）」を参照                                                                                    |
| それ以外                 | アプリ本体の SPA                                                                              | `hono/jsx/dom`（`src/client/`）。Static Assets として配信                                                                                         |

### D1 のスキーマ（`migrations/0001_init.sql`）

- **Better Auth の表**: `user` / `session` / `account` / `verification`
- **アプリの表**: `notes`（共有の単位）、`note_members`、`pages`、`dev_outbox`（開発時のみ、メールの代わりにマジックリンクを保存）
- **一覧**: `pages_note_recent (note_id, updated_at DESC, id DESC)` 索引を使うキーセット方式で、`OFFSET` は使いません
- **件数**: `notes.page_count` をトリガーで更新し、`COUNT(*)` で全件を数えません
- **全文検索**: FTS5 の `trigram` トークナイザで、形態素解析なしで日本語を検索します。本文の複製を持たない外部コンテンツ型で、トリガーで同期します。参照先の rowid には、VACUUM で変わらない `pages.seq`（INTEGER PRIMARY KEY）を使います
- **短い語の検索**: trigram は 3 文字未満の語に一致しないため、その語だけ `LIKE`（エスケープ付き）で絞り込みます

Drizzle のスキーマ（`src/worker/db/schema.ts`）は SQL と対にしています。FTS5 とトリガーは SQL にだけあります。

### クライアント

使っている外部ライブラリはすべてフレームワーク非依存です。

- `@tanstack/query-core`（通常のクエリとカーソル方式の無限クエリ）と `@tanstack/virtual-core`。それぞれ薄いフックで包んでいます
- `@floating-ui/dom`
- Tiptap 3 本体（React バインディングは使わない）+ Y.js + `y-partyserver/provider` + `y-indexeddb`
- `marked`: 字句解析だけを使います（後述）

Y.js のエディタ連携（`@tiptap/y-tiptap`）には小さなパッチを当てています。`patchedDependencies`（`patches/`）でインストール時に適用されます。詳細は所見の「大きな文書」を参照してください。

`better-auth/client` はサインイン・サインアウトの時だけ遅延読み込みします。ルーター、遅延読み込み、コマンドパレット（ネイティブ `<dialog>` + ARIA の combobox/listbox）は自作で、UI ライブラリは使っていません。

自作した主な部品は次の 2 つです。

- **Markdown のストリーミング表示**（`src/client/markdown/`）
  - `blockSplitter`: 流れてくる Markdown を、CommonMark でもブロックが切れる位置でだけ分割します。コードブロック、ゆるいリスト、setext 見出しは分けません。そのため、ブロック単位で描画しても全文を描画した結果と一致します
  - `renderMarkdown`: `marked` のトークンから DOM を直接組み立てます。`innerHTML` は使わず、生の HTML は文字として表示し、危険なスキームのリンクは捨てます。そのためサニタイザは不要です
  - `markdownStream`: 確定したブロックは一度だけ描画して固定し、未確定の末尾ブロックだけを毎フレーム描き直します
- **カーソル共有**（`src/client/editor/sharedCarets.ts`）: Tiptap 標準の CollaborationCaret と同じ通信形式・見た目で、次の 2 点を変えた軽量版です
  - 自分のカーソル位置は、入力が止まってから（150ms）送信します
  - 自分の awareness（在席・カーソル情報の共有）の変更では再描画しません

### オフライン（PWA）

マニフェストとアイコンは `src/client/public/` にあります。Service Worker（`src/client/sw/sw.ts`）は別エントリとしてビルドし、保存一覧とキャッシュのバージョンはビルド時に埋め込みます（`vite.config.ts`）。`sw.js` が共有チャンクを import する形になった場合はビルドを失敗させ、従来型スクリプトとして読み込めることを保証します。

| リクエスト                                                 | 方式（`src/client/sw/strategy.ts`）                                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `/assets/*`（ハッシュ付きのビルド成果物）                  | インストール時に保存し、キャッシュ優先                                                               |
| 画面遷移                                                   | ネットワーク優先。オフライン時は保存したアプリシェル（`/` はオンラインなら SSR、オフラインなら SPA） |
| `/api/me`・`/api/notes/:id/pages`・`/api/pages/:id`（GET） | ネットワーク優先で、最後の 200 応答を保持。401 を受けたら API キャッシュを削除                       |
| 認証・検索・AI・リアルタイム・すべての書き込み・他オリジン | 扱わない（そのままネットワークへ）                                                                   |

このほか:

- **ページ本文**: 開いたページごとに Y.js の複製を IndexedDB に保持します（`y-indexeddb`、`zedi:page:<id>`）。オフラインでも開いて編集でき、WebSocket が再接続すると Y.js が編集を統合します。
- **ページ作成**: オンラインかどうかにかかわらず、クライアント生成の UUID で永続キュー（`src/client/lib/outbox.ts`）を通します。`POST /api/notes/:noteId/pages` はこの id を受け付け、冪等です（新規 201、再送 200、別ノートの id は 409、不正な形式は 400）。エディタはすぐに開き、サーバーがまだ知らないページは「未同期」と表示して、ページができてからルームに接続します。キューは起動時・接続回復時・作成のたびに送り、拒否（4xx）は利用者に表示します。
- **クエリ**は TanStack Query の `offlineFirst` モードで実行し、Service Worker が応答できるようにしています。検索がサーバーに届かないときは、`⌘K` が端末にあるページのタイトルと冒頭を照合します。
- **セッション**: オフラインでは `/api/me` をキャッシュから返します。キャッシュもなければ、接続できない旨と再試行ボタンを表示します。
- **サインアウト**はオフライン中は無効です（未同期の編集が失われるため）。実行すると API キャッシュとページのローカル複製をすべて削除します。

### 長いコンテンツ（`src/shared/import/splitDocument.ts`）

大きな文書の計測結果をもとにした、Web クリップや PDF のテキストをページに分ける仕様です。

- **単位**: テキストブロック（段落、見出し、リスト項目の段落など）。テキストを持たないブロックは 1 と数えます。編集コストはこの数に比例します。
- **上限**: 1,000 ブロックまでは 1 ページのまま。超えるとエディタに警告を出します（`src/client/editor/pageSize.ts`。編集が止まってから 1 秒後に数え直す）。
- **切る位置**: 文書で使われている最上位の見出しの前で切ります。800 ブロックを超える節は、1 段下の見出しで切り直します。同じ章の連続する節は 800 ブロックまで 1 ページに詰めます（上位の見出しはまたがない）。見出しのない本文は均等に切ります。トップレベルのブロックは分割せず、1 ページより大きいブロックは単独のページにします。
- **ページ**: 目次ページ（元のタイトル）が全パートを列挙します。各パートのタイトルは `タイトル (2/5): 最初の見出し` で、先頭に目次へのリンク、末尾に前後のパートへのリンクを置きます。id はオフライン作成と同じくクライアントで生成します。

## 実装した機能

- マジックリンクでのサインイン・サインアウトと、初回サインイン時の既定ノート作成（Better Auth の database hook）
- D1 のページ一覧（100 件ずつ取得 + 仮想スクロール）と新規ページ作成
- `⌘K` の全文検索（アクセスできる全ノートが対象）
- 共同編集エディタ: WikiLink（`[[` で候補を全文検索）、`/` コマンド、`#タグ`、複数人のカーソル
- ノートの共有（閲覧者・編集者）。権限がなければ API も WebSocket も 404 を返し、存在を漏らしません
- AI 応答のストリーミング表示。テキストは 3 方式、Markdown は 2 方式（`md-blocks` / `md-naive`）
- PWA としてのオフライン利用: 一覧と開いたことのあるページの閲覧、オフラインでの編集とページ作成、再接続時の同期
- エディタの長文警告と、長い取り込みコンテンツの分割処理（取り込み UI 自体は未実装）

**対象外**: 実際のメール送信（Email Service）と Google OAuth の往復（外部アカウントと外部への通信が必要）、実際の LLM 呼び出し、コードのシンタックスハイライト、i18n。Tauri は要件から外しました。

## コマンド

```bash
bun install
cp .dev.vars.example .dev.vars   # BETTER_AUTH_SECRET（ローカル用）
bun run test          # 単体テスト（Node / happy-dom）+ 統合テスト（workerd 上で D1・DO を使用）
bun run typecheck     # クライアント（hono/jsx/dom）とワーカー（hono/jsx）を別々に型チェック
bun run build         # SPA を dist/client にビルド
bun run db:migrate    # ローカル D1 にマイグレーションを適用
bun run dev:worker    # wrangler dev（http://127.0.0.1:8787）
bun run smoke         # 空の D1 でサインインからサインアウトまでをブラウザで確認（build 済みが前提）
bun run bundle:report # バンドルサイズ → results/bundle.json
bun run measure       # D1 に 1 万ページを投入して API とブラウザを計測 → results/measurements.json
# 大きな文書の分析（CPU 4 倍スロットリング） → results/large-documents.json
ONLY=largeDoc CPU_RATES=4 OUTPUT=results/large-documents.json bun run measure
# 入力中の CPU プロファイル（圧縮なしでビルドしてから）
bunx vite build --minify false && node scripts/profileTyping.mjs
# y-tiptap パッチの前後比較: パッチを戻したビルドと当てたビルドを用意し、
# それぞれで交互に実行 → results/y-tiptap-patch.json
ONLY=largeDocPatch CPU_RATES=4 SEED_PAGES=10 bun run measure
```

`smoke` と `measure` は Playwright と Chromium を使います。`CHROMIUM_PATH` で既存の Chromium を指定できます。どちらも実行のたびに空のローカル D1（`.wrangler/runs/`）を用意します。

調査用に、エディタの URL で次の切り替えができます。

- `?caret=tiptap`: Tiptap 標準のカーソル共有
- `?caret=0`: カーソル共有なし
- `?collab=0`: Y.js なし
- `?cv=1`: `content-visibility`

## 計測結果（2026-10-30）

計測環境: コンテナ上のヘッドレス Chromium + ローカルの workerd / D1（`wrangler dev`）。ネットワーク遅延は含みません。「4x」は CDP の CPU スロットリングです。生データは `results/` にあります。

- **API の遅延はローカルの値で、実際の D1 での値ではありません。** D1 が返す読み取り行数は実行環境に依存しないので、クエリの効率を比べる指標として扱います。
- **この README の数値は、今回のセッションの VM で計測したものです。** 前のコミットの README とは VM が違い（今回のほうが遅い）、直接は比較できません。
- **4x の入力遅延は、同じ構成でも実行ごとに 2〜3 倍ばらつきます。** そのため主要な比較は 3 回分の値を併記し、比較は同じ実行内の相対値で示します。いずれの比較も、方向は 3 回とも一致しました。

| テキスト `blocks`（段落ごとにブロックを分ける）   | 60 / 60 fps                | 51 fps            | **47 fps**                                    |
| Markdown `md-naive`（毎フレーム全文を解析・描画） | 60 / 51 fps                | 31〜32 fps        | **16〜17 fps**（長いタスク合計 22〜24 秒）    |
| Markdown `md-blocks`（確定ブロックを固定）        | 60 / 60 fps                | 50〜54 fps        | **49〜53 fps**（長いタスク合計 0.15〜0.3 秒） |

Markdown の 4x の値は 3 回分の範囲です。今の React 版の `react-markdown` は、メッセージが更新されるたびに全文を解析し直すので、`md-naive` と同じ考え方です。

## わかったこと

### 認証（Better Auth）

1. **Better Auth は Workers + D1 でそのまま動きました。** Kysely を含まない `better-auth/minimal` と Drizzle アダプタを使えば、クエリ層を Drizzle に統一できます。
2. **セッションは Cookie キャッシュ（5 分）で D1 を読みません。** `/api/me` の読み取りは既定ノートの 1 行だけでした。
3. **WebSocket もセッション Cookie で認可できます。** フロントと API が同じオリジンだからです。今の Hocuspocus のように、別サービスから `session` テーブルを直接読んだり、権限ロジックを二重に持ったりする必要がなくなります。

### D1

4. **キーセット方式なら、どこまでスクロールしても 1 回あたりの読み取りは約 100 行です**（5,000 件目以降でも 103 行）。
5. **FTS5 trigram は日本語でも索引が効きます**（読み取り 41 行）。一方で **2 文字以下の語は索引が使えず**、ヒットしなければノート内の全ページを読みます（10,004 行）。D1 は読み取り行数で課金されるので、次のどちらかが必要です。
   - 2 文字検索をタイトルに限る、または最近のページに限る
   - 2-gram の索引を別に持つ
6. **書き込みが約 5 倍に増えます**（1 ページで約 5 行）。DO からの書き戻しは本文が変わったときだけに絞っています。
7. **D1 には BEGIN/COMMIT 形式のトランザクションがなく、1 文で渡せる値も 100 個までです。** 複数の更新はトリガー・`batch()`・条件付き UPDATE で組み立てています。冪等なページ作成も、`INSERT … ON CONFLICT DO NOTHING` と所有ノートの確認を 1 回の `batch()` で行っています。

### AI 応答のストリーミング表示

8. **重さの原因は「毎回全文を処理すること」です。** フレームワークの描画方式ではありません。テキストでも Markdown でも、全文を描き直す方式は応答が長くなるほど劣化し、4x・10,000 トークンでは 15〜17fps まで落ちます。
9. **`md-blocks` は応答の長さによらず、4x でも 50fps 前後を保ちます。** 確定ブロックを一度だけ描画して固定し、未確定の末尾だけを解析・描画するためです。本番の AI チャットはこの方式にすべきです。今の `react-markdown` を使った実装は、長い応答で同じ劣化が起きるはずです。
10. **Markdown は「トークンから DOM を直接組み立てる」方式にすれば、サニタイザなしで安全に描画できます。** `marked` の字句解析を含めても AI チャットのチャンクは gzip 16.6KB です。ブロック分割は CommonMark でもブロックが切れる位置だけで行うので、確定済みのブロックを後から描き直す必要がありません。

### 大きな文書

11. **Tiptap 標準のカーソル共有は、大きな文書でいちばん重い部分です。** 原因は次の 3 つです。
    - キーを打つたびに、自分のカーソル位置を文書の先頭から走査して変換している（位置に比例するコスト）
    - そのたびに awareness を送信している
    - 自分の awareness の変更にも反応して余分なトランザクションを発行し、装飾を全体に描き直している
12. **自前の軽量カーソル共有に置き換えると、入力遅延は 2.2〜3.3 倍改善しました**（同期層パッチ前の中央値で 467 → 176ms）。通信形式は Tiptap と同じです。
13. **Y.js の同期層は、ローカル入力では不要な「選択位置の相対位置への変換」を 1 打鍵に 3 回行っていました。** `@tiptap/y-tiptap` は、Yjs のトランザクションの前、ローカル編集を反映した後、そして undo プラグインでエディタのトランザクションごとに、毎回文書の先頭から走査して変換していました。`patches/` のパッチ（約 60 行）は次のように変えます。
    - 1 回目: エディタ自身のトランザクションでは省く
    - 2 回目: 入れ子のトランザクションや参照があるまで遅らせる（エディタの変更が他の Yjs 編集と外側のトランザクションを共有する場合は従来どおり即時）
    - 3 回目: 新しい undo ステップを始める変更のときだけ行う（予測が外れた場合は、そのステップでカーソルが戻らないだけ）

    相手の編集・undo/redo・共有トランザクションのいずれでもカーソル位置が保たれることを単体テストで確認しています。`@tiptap/y-tiptap` は y-prosemirror のフォークなので、同じ変更が上流にも当てはまる可能性が高く、提案する価値があります。

14. **パッチ後は、2,000 段落でも共同編集のコストはローカル編集とほぼ変わりません。** カーソル共有なしで 177 → 71 ms（ローカル編集は 62〜67 ms）、軽量カーソル共有で 130 → 90 ms、Tiptap 標準で 388 → 196 ms です。
15. **4,000 段落ではまだ入力が溜まります（p50 約 1 秒。パッチ前は 3〜4 秒）。** 残りのコストは今回プロファイルしていません。同期層は変更のたびにトップレベルの子をすべて突き合わせており（`updateYFragment`）、これが文書の大きさに比例します。
16. **`content-visibility: auto` は逆効果でした。** ProseMirror がカーソル位置を計算するときに、省いたレイアウトを強制的にやり直させるためと考えられます。
17. **文書サイズの目安は実装済みです。** 1,000 テキストブロックを超えるとエディタが警告し、長い取り込みは「長いコンテンツ」の規則で分割します。Zedi の「1 ページ 1 アイデア」の方針にも合います。

### オフライン（PWA）

18. **手書きの 1.6KB の Service Worker で足ります（Workbox 不要）。** 落とし穴は、アプリと共有するモジュールが別チャンクになり、従来型の Service Worker からは import できないことです。ビルドでこれを検査し、アプリ側は定数を import せず名前の接頭辞でキャッシュを消します。
19. **Static Assets の SPA フォールバックでは、`/index.html` はアプリシェルになりません。** 既定の HTML の扱いでは `/` にリダイレクトされ、ここでの `/` は Worker の SSR ページです。代わりに `/notes`（任意の SPA ルート）をシェルとして保存しています。
20. **クライアント生成の id にすると、オフラインでのページ作成が単純になります。** オンラインとオフラインで処理が 1 本になり、サーバーの挿入は冪等で、ルームへの接続はページができてからです。本文は Y.js が統合するので、本文の競合処理は不要です。
21. **TanStack Query は、ブラウザがオフラインと判断している間はクエリを止めます。** `networkMode: "offlineFirst"` にすると実行され、Service Worker がキャッシュから応答できます。
22. **プロバイダは一度接続してからでないと切断を通知しません。** そのため、エディタのオフライン表示は `navigator.onLine` にも従わせています。
23. **オフライン用のデータはブラウザ内に平文で残ります。** API 応答のキャッシュと Y.js のローカル複製はサインアウト時に、API キャッシュは 401 を受けたときにも削除します。未同期の編集を黙って捨てないよう、オフライン中のサインアウトは禁止しています。保存データの暗号化と、ストレージの退避（eviction）への対策は未対応です。

### 開発環境の落とし穴

24. **統合テスト用パッケージが改名されていました。** `@cloudflare/vitest-pool-workers` は `@cloudflare/vitest-plugin` になっています。また、同梱の workerd が対応する互換日付（compatibility date）が wrangler より古いことがあります。
25. **Worker 側の TSX は `hono/jsx`、クライアント側は `hono/jsx/dom` です。** `wrangler.jsonc` で `tsconfig` を指定しないと、Worker が `React is not defined` で落ちます。
26. **4x の CPU スロットリングは、共有 VM 上では実行ごとのばらつきが大きいです。** 性能の判断は、同じ実行内の比較と、交互に繰り返した計測で行ってください。
27. **lib0 は読み込み時に `Date.now` を取り込むため、フェイクタイマーでは Yjs の undo のまとめ時間を動かせません。** テストでは、入力の一時停止と同じ効果を持つ `UndoManager.stopCapturing()` で新しい undo ステップを始めています。
28. **依存パッケージ内部の呼び出しを観察するには、インライン化が必要です。** 単体テストでは `@tiptap/y-tiptap` と `@tiptap/extension-collaboration` を Vite で処理させ（`server.deps.inline`）、`vi.mock("yjs")` が届くようにしています。

### フロントエンド全体

29. **`hono/jsx/dom` はどのシナリオでもボトルネックになっていません。** 重かった箇所の原因は、いずれもフレームワーク以外でした（全文の再描画、レイアウト、Y.js の同期層）。
