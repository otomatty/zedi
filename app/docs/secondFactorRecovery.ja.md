# すべての確認方法を失った人の復旧

Zedi は Google のサインインのあとに、パスキーか認証アプリでの確認を求めます（[../README.ja.md](../README.ja.md) の「2 段階認証」）。確認方法と復旧用コードを**すべて**失った人はサインインできません。その場合は管理者（otomatty）が本人を確認し、2 段階目を消します。管理画面ができるまでは、D1 に対してスクリプトで行います。

復旧用コードが 1 つでも残っていれば、この手順は要りません。そのコードでサインインし、セキュリティの画面で新しい確認方法を登録して、コードを作り直してもらいます。

## 消すものと残すもの

- 利用者のパスキー、認証アプリ、復旧用コード、試行の回数を消します。
- 利用者のすべてのセッションを終えます。古いセッションは 2 段階目の API にまったく届かなくなる（その API は D1 からセッションを読む）ので、確認方法がない間に登録することはできません。それ以外の画面では、サインインしていたブラウザは 5 分以内に使えなくなります（セッションの Cookie キャッシュのため。otomatty/zedi#1176）。
- アカウント、Google との結び付き、ノートとページは残します。
- 確認方法がなくなるので、次に Google でサインインすると、初回と同じように最初の確認方法を登録し、新しい復旧用コード 10 個が表示されます。

**注意:** リセットしてから利用者が新しい方法を登録するまでは、Google だけで確認方法を登録できます。利用者がすぐにサインインできるときにだけリセットし、あとで登録されたことを確かめてください。

## 1. 本人を確認する

Google でサインインできることは 1 段階目の証明にしかならず、それだけでは足りません。次をすべて行います。

1. **アカウントのアドレスにだけ連絡する。** 依頼の中に書かれた別のアドレスではなく、アカウントのアドレスに返信し、そのアドレスから確認してもらいます。
2. **Google でサインインしてもらう。** 2 段階目の確認画面まで進めるはずです。下の手順 2 でセッションの数を見れば、新しいセッションができたことがわかります。
3. **本人しか知らないことを聞き**、手順 2 の表示と照らし合わせる。たとえば、いつごろ使い始めたか、どの確認方法を持っていたか（パスキーの数、認証アプリの有無）。
4. **返信から 24 時間以上待つ。** 依頼が本人のものでなければ、本人が止められるようにするためです。対面など、信頼できる方法で本人を確かめた場合だけ待たずに進めます。
5. **記録はこのリポジトリの外に残す**（Git に個人情報を入れない）。日付、アドレス、確認の方法、リセットした時刻を書きます。

食い違いがあれば、リセットしません。

## 2. アカウントを見る

`wrangler` を Cloudflare のアカウントにサインインさせておきます（`bunx wrangler login`）。`app/` で次を実行します。

```bash
node scripts/resetSecondFactor.mjs --email user@example.com --remote --env production --dry-run
```

アカウント（ID、登録日、パスキーの数、認証アプリの有無、残りの復旧用コード、セッションの数）と、実行される SQL を表示します。何も変えません。本番の D1 はデプロイの準備（otomatty/zedi#1157）で作るので、それまではリモートにリセットする相手はいません。

## 3. リセットする

利用者がすぐサインインできるときに実行します。

```bash
node scripts/resetSecondFactor.mjs --email user@example.com --remote --env production
```

スクリプトは次の順に進みます。

1. アカウントをもう一度表示する
2. アドレスをもう一度入力させる
3. 削除を 1 つのファイルとして実行する（失敗すると D1 がファイル全体を元に戻すので、やり直しても安全です）
4. 実行後のアカウントを表示する（すべて 0 になっているはずです）

ふつうのアドレスでないものや、どの利用者にも当てはまらないアドレスでは止まります。

## 4. リセットのあと

1. すぐに Google でサインインし、パスキーか認証アプリを登録して、新しい復旧用コードを保存するよう伝えます。両方の登録を勧めます。
2. `--dry-run` のコマンドをもう一度実行します。新しい確認方法と、復旧用コード 10 個が表示されるはずです。それまでは Google だけで確認方法を登録できるので、数時間たっても登録されなければ連絡します。
3. リセットした時刻と、新しく登録された時刻を記録に足します。

## ローカルで練習する

同じスクリプトをローカルの D1 にも使えます。`bun run dev:worker` が使うデータベースに対しては次のとおりです。

```bash
node scripts/resetSecondFactor.mjs --email someone@test.zedi-note.app --local
```

ほかのローカルのデータベース（スモークテストが `.wrangler/runs/` に残すものなど）には `--persist-to <dir>` を付けます。

## 確かめ方

SQL は `src/worker/secondFactor/adminReset.ts` が組み立てます。

- 単体テストで、アドレスの確認、引用符の扱い（アドレスにアポストロフィがある場合など）、どの表に触れるかを確かめています。
- `src/worker/integration/adminReset.worker.test.ts` は、同じ SQL を本物のスキーマに対して実行します。その利用者の確認方法・コード・セッションだけが消えること、アカウントとノートが残ること、次の Google のサインインで最初の確認方法と新しいコードを登録できることを確かめています。

スキーマを変えたときは、これらのテストでリセットがまだ足りているかがわかります。
