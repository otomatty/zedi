# Zedi アプリ（作り直し）

Zedi を Cloudflare Worker 1 本の構成で作り直したアプリです。画面（`hono/jsx/dom`）、API（Hono）、認証（Better Auth）、データ（D1）、共同編集（Durable Objects）をまとめて配信します。対象は Web アプリ（PWA）のみです。

現行アプリ（リポジトリ直下の `src/`、`server/*`、`admin/`）の機能をここに移し、揃った時点でドメインをこのアプリに切り替え、リポジトリ直下に移します。本番にデータがないため、データ移行はありません。構成を決めるための検証（計測値と分かったこと）は [docs/verification.ja.md](docs/verification.ja.md) にあります。

## 構成

Cloudflare Worker 1 本ですべてを配信します（`wrangler.jsonc`）。フロントと API が同じオリジンなので、CORS の設定やサードパーティ Cookie は不要です。

| パス                     | 中身                                                                                          | 技術                                                                                                                                                   |
| ------------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/`                      | 公開ページ（JS なし）                                                                         | Worker 上で `hono/jsx` によるサーバー描画（`src/worker/landing.tsx`）                                                                                  |
| `/api/auth/*`            | 認証                                                                                          | Better Auth（`better-auth/minimal` + Drizzle アダプタ + D1）。Google でサインイン（資格情報を設定したときだけ有効）。本番以外ではテスト用 IdP も使える |
| `/test-idp/authorize`    | テスト用 IdP のサインイン画面                                                                 | `TEST_IDP` バインディングがあるときだけ、テスト用 IdP の Worker に転送する。本番にはバインディングがないので 404                                       |
| `/api/*`                 | ページ一覧・作成・詳細、共有メンバー、全文検索、疑似 AI ストリーミング（テキスト / Markdown） | Hono（`src/worker/app.tsx`）+ D1。全ルートでセッション必須、ノート単位の認可                                                                           |
| `/parties/page-room/:id` | 共同編集                                                                                      | ページごとの Durable Object（`PageRoom`）。接続時にセッションとページの権限を確認し、閲覧者は書き込み不可。保存時に本文のテキストを D1 に書き戻す      |
| `/sw.js`                 | Service Worker（オフライン）                                                                  | `src/client/sw/` からビルド。後述の「オフライン（PWA）」を参照                                                                                         |
| それ以外                 | アプリ本体の SPA                                                                              | `hono/jsx/dom`（`src/client/`）。Static Assets として配信                                                                                              |

### サインイン

- **本番は Google だけ**です。資格情報（`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`）を設定したときに有効になります。Google のアカウントがあれば誰でも登録できます。マジックリンクは廃止しました。
- **ローカルと試験ではテスト用 IdP** でもサインインできます。Google の代わりをする小さな OAuth プロバイダーで、別の Worker（`src/testIdp/`、`wrangler.test-idp.jsonc`）として動きます。Preview と staging には、それぞれの環境を作るときに入れます（otomatty/zedi#1157）。
  - アプリからは `TEST_IDP` サービスバインディングで呼び、Better Auth の `genericOAuth` でつなぎます。ブラウザに見せるのはサインイン画面（`/test-idp/authorize`）だけで、アプリが同じオリジンで転送します。トークンとユーザー情報はバインディング経由でしか取れません。
  - 戻り先は、リクエストが届いたのと同じオリジンのコールバックに限ります。サインインには `.dev.vars` の `TEST_IDP_PASSWORD` が必要で、`@test.zedi-note.app` のアドレスしか作れません。
  - 本番の環境（`wrangler.jsonc` の `env.production`）には `TEST_IDP` を置きません。単体テストでこれを確かめています。
- `wrangler.jsonc` の最上位はローカル用（`zedi-app-local`）です。デプロイする環境は `env` の下にあり、`--env` を付けたときだけ使われます。

### D1 のスキーマ（`migrations/`）

- **Better Auth の表**: `user` / `session` / `account` / `verification`
- **アプリの表**: `notes`（共有の単位）、`note_members`、`pages`
- **一覧**: `pages_note_recent (note_id, updated_at DESC, id DESC)` 索引を使うキーセット方式で、`OFFSET` は使いません
- **件数**: `notes.page_count` をトリガーで更新し、`COUNT(*)` で全件を数えません
- **全文検索**: FTS5 の `trigram` トークナイザで、形態素解析なしで日本語を検索します。本文の複製を持たない外部コンテンツ型で、トリガーで同期します。参照先の rowid には、VACUUM で変わらない `pages.seq`（INTEGER PRIMARY KEY）を使います
- **短い語の検索**: trigram は 3 文字未満の語に一致しないため、その語だけ `LIKE`（エスケープ付き）で絞り込みます

Drizzle のスキーマ（`src/worker/db/schema.ts`）は SQL と対にしています。FTS5 とトリガーは SQL にだけあります。

### クライアント

使っている外部ライブラリはすべてフレームワーク非依存です。

- `@tanstack/query-core`（通常のクエリとカーソル方式の無限クエリ）と `@tanstack/virtual-core`。それぞれ薄いフックで包んでいます
- `@floating-ui/dom`
- Tiptap 3 本体（React バインディングは使わない）+ Y.js + `y-partyserver/provider` + `y-indexeddb`
- `marked`: 字句解析だけを使います（後述）

Y.js のエディタ連携（`@tiptap/y-tiptap`）には小さなパッチを当てています。`patchedDependencies`（`patches/`）でインストール時に適用されます。詳細は [docs/verification.ja.md](docs/verification.ja.md) の「大きな文書」を参照してください。

`better-auth/client` はサインイン・サインアウトの時だけ遅延読み込みします。ルーター、遅延読み込み、コマンドパレット（ネイティブ `<dialog>` + ARIA の combobox/listbox）は自作で、UI ライブラリは使っていません。

自作した主な部品は次の 2 つです。

- **Markdown のストリーミング表示**（`src/client/markdown/`）
  - `blockSplitter`: 流れてくる Markdown を、CommonMark でもブロックが切れる位置でだけ分割します。コードブロック、ゆるいリスト、setext 見出しは分けません。そのため、ブロック単位で描画しても全文を描画した結果と一致します
  - `renderMarkdown`: `marked` のトークンから DOM を直接組み立てます。`innerHTML` は使わず、生の HTML は文字として表示し、危険なスキームのリンクは捨てます。そのためサニタイザは不要です
  - `markdownStream`: 確定したブロックは一度だけ描画して固定し、未確定の末尾ブロックだけを毎フレーム描き直します
- **カーソル共有**（`src/client/editor/sharedCarets.ts`）: Tiptap 標準の CollaborationCaret と同じ通信形式・見た目で、次の 2 点を変えた軽量版です
  - 自分のカーソル位置は、入力が止まってから（150ms）送信します
  - 自分の awareness（在席・カーソル情報の共有）の変更では再描画しません

### オフライン（PWA）

マニフェストとアイコンは `src/client/public/` にあります。Service Worker（`src/client/sw/sw.ts`）は別エントリとしてビルドし、保存一覧とキャッシュのバージョンはビルド時に埋め込みます（`vite.config.ts`）。`sw.js` が共有チャンクを import する形になった場合はビルドを失敗させ、従来型スクリプトとして読み込めることを保証します。

| リクエスト                                                 | 方式（`src/client/sw/strategy.ts`）                                                                  |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `/assets/*`（ハッシュ付きのビルド成果物）                  | インストール時に保存し、キャッシュ優先                                                               |
| 画面遷移                                                   | ネットワーク優先。オフライン時は保存したアプリシェル（`/` はオンラインなら SSR、オフラインなら SPA） |
| `/api/me`・`/api/notes/:id/pages`・`/api/pages/:id`（GET） | ネットワーク優先で、最後の 200 応答を保持。401 を受けたら API キャッシュを削除                       |
| 認証・検索・AI・リアルタイム・すべての書き込み・他オリジン | 扱わない（そのままネットワークへ）                                                                   |

このほか:

- **ページ本文**: 開いたページごとに Y.js の複製を IndexedDB に保持します（`y-indexeddb`、`zedi:page:<id>`）。オフラインでも開いて編集でき、WebSocket が再接続すると Y.js が編集を統合します。
- **ページ作成**: オンラインかどうかにかかわらず、クライアント生成の UUID で永続キュー（`src/client/lib/outbox.ts`）を通します。`POST /api/notes/:noteId/pages` はこの id を受け付け、冪等です（新規 201、再送 200、別ノートの id は 409、不正な形式は 400）。エディタはすぐに開き、サーバーがまだ知らないページは「未同期」と表示して、ページができてからルームに接続します。キューは起動時・接続回復時・作成のたびに送ります（送信中に作ったページも同じ回で送る）。再試行で直らない拒否（400・403・404・409・410・413・422）はキューから外して利用者に表示し、401（オフライン中のセッション切れ）・408・425・429・5xx・通信失敗では次の同期まで保持します。
- **クエリ**は TanStack Query の `offlineFirst` モードで実行し、Service Worker が応答できるようにしています。検索がサーバーに届かないときは、`⌘K` が端末にあるページのタイトルと冒頭を照合します。
- **セッション**: オフラインでは `/api/me` をキャッシュから返します。キャッシュもなければ、接続できない旨と再試行ボタンを表示します。
- **サインアウト**はオフライン中は無効です（未同期の編集が失われるため）。サーバーがセッションの終了を確認してから、API キャッシュ・ページのローカル複製・未送信のページの一覧をすべて削除します。失敗したときはサインイン状態のまま、その旨を表示します。

### 長いコンテンツ（`src/shared/import/splitDocument.ts`）

大きな文書の計測結果をもとにした、Web クリップや PDF のテキストをページに分ける仕様です。

- **単位**: テキストブロック（段落、見出し、リスト項目の段落など）。テキストを持たないブロックは 1 と数えます。編集コストはこの数に比例します。
- **上限**: 1,000 ブロックまでは 1 ページのまま。超えるとエディタに警告を出します（`src/client/editor/pageSize.ts`。編集が止まってから 1 秒後に数え直す）。
- **切る位置**: 文書で使われている最上位の見出しの前で切ります。800 ブロックを超える節は、1 段下の見出しで切り直します。同じ章の連続する節は 800 ブロックまで 1 ページに詰めます（上位の見出しはまたがない）。見出しのない本文は均等に切ります。トップレベルのブロックは分割せず、1 ページより大きいブロックは単独のページにします。
- **ページ**: 目次ページ（元のタイトル）が全パートを列挙します。各パートのタイトルは `タイトル (2/5): 最初の見出し` で、先頭に目次へのリンク、末尾に前後のパートへのリンクを置きます。id はオフライン作成と同じくクライアントで生成します。

## 実装済みの機能

- Google（本番以外ではテスト用 IdP）でのサインイン・サインアウトと、初回サインイン時の既定ノート作成（Better Auth の database hook）
- D1 のページ一覧（100 件ずつ取得 + 仮想スクロール）と新規ページ作成
- `⌘K` の全文検索（アクセスできる全ノートが対象）
- 共同編集エディタ: WikiLink（`[[` で候補を全文検索）、`/` コマンド、`#タグ`、複数人のカーソル
- ノートの共有（閲覧者・編集者）。権限がなければ API も WebSocket も 404 を返し、存在を漏らしません
- AI 応答のストリーミング表示。テキストは 3 方式、Markdown は 2 方式（`md-blocks` / `md-naive`）
- PWA としてのオフライン利用: 一覧と開いたことのあるページの閲覧、オフラインでの編集とページ作成、再接続時の同期
- エディタの長文警告と、長い取り込みコンテンツの分割処理（取り込み UI 自体は未実装）

**未実装**: 現行アプリから移す機能の大半（実際の LLM 呼び出し、AI での下書き生成、Web クリップ、課金、管理画面、MCP など）、2 段階認証（otomatty/zedi#1156）、本物の Google での往復の確認（staging で手作業）、コードのシンタックスハイライト、i18n。

## コマンド

```bash
bun install
cp .dev.vars.example .dev.vars   # BETTER_AUTH_SECRET・ENVIRONMENT=development・テスト用 IdP の値（ローカル用）
bun run test          # 単体テスト（Node / happy-dom）+ 統合テスト（workerd 上で D1・DO を使用）
bun run typecheck     # クライアント（hono/jsx/dom）・ワーカー（hono/jsx）・Node で動くテストを別々に型チェック
bun run build         # SPA を dist/client にビルド
bun run db:migrate    # ローカル D1 にマイグレーションを適用
bun run dev:worker    # アプリとテスト用 IdP を wrangler dev で起動（http://127.0.0.1:8787）
bun run smoke         # 空の D1 でサインインからサインアウトまでをブラウザで確認（build 済みが前提）
bun run bundle:report # バンドルサイズ → results/bundle.json
bun run measure       # D1 に 1 万ページを投入して API とブラウザを計測 → results/measurements.json
# 大きな文書の分析（CPU 4 倍スロットリング） → results/large-documents.json
ONLY=largeDoc CPU_RATES=4 OUTPUT=results/large-documents.json bun run measure
# 入力中の CPU プロファイル（圧縮なしでビルドしてから）
bunx vite build --minify false && node scripts/profileTyping.mjs
# y-tiptap パッチの前後比較: パッチを戻したビルドと当てたビルドを用意し、上書きしないよう
# 回ごとに別の OUTPUT（N は回数）で交互に実行する。各回の `largeDocPatch` を
# results/y-tiptap-patch.json の `runs.orig` / `runs.patched` にまとめ、`medianP50` を計算し直す。
ONLY=largeDocPatch CPU_RATES=4 SEED_PAGES=10 OUTPUT=results/raw/patch-orig-N.json bun run measure
ONLY=largeDocPatch CPU_RATES=4 SEED_PAGES=10 OUTPUT=results/raw/patch-on-N.json bun run measure
```

`smoke` と `measure` は Playwright と Chromium を使います。`CHROMIUM_PATH` で既存の Chromium を指定できます。どちらも実行のたびに空のローカル D1（`.wrangler/runs/`）を用意します。

調査用に、エディタの URL で次の切り替えができます。

- `?caret=tiptap`: Tiptap 標準のカーソル共有
- `?caret=0`: カーソル共有なし
- `?collab=0`: Y.js なし
- `?cv=1`: `content-visibility`

## テスト

CI（`.github/workflows/ci.yml`）の `app-test` が型チェック・単体テスト・統合テスト・ビルドを、`app-smoke` がブラウザのスモークテストを実行します。

| 種類                                       | 件数    | 内容                                    |
| ------------------------------------------ | ------- | --------------------------------------- |
| 単体（Vitest、Node / happy-dom）           | 191     | 下記                                    |
| 統合（Vitest、workerd 上で D1・DO を使用） | 26      | マイグレーションは本番と同じ SQL を適用 |
| ブラウザ（`bun run smoke`）                | 18 項目 | 下記                                    |

単体テストの対象:

- ルーター（不正なパーセントエンコードで止まらないこと）、データ取得や仮想リストのアダプタ、SSE パーサー、フレーム単位の追記
- ページの遅延読み込み（失敗時のエラー表示と再試行）
- 検索方法の判定、カーソル、100 パラメータ分割、Y.js からのテキスト抽出
- Markdown
  - ブロック分割: 全文の描画との一致、1 文字ずつ流しても同じ結果になること
  - 描画の安全性: 生の HTML、`javascript:` リンク、`//host` と `/\host` のリンク
  - 確定ブロックの固定
- カーソル送信のスケジューリング
- パッチ後の共同編集の選択範囲: 相手の編集後や、エディタの変更と Yjs の直接編集が 1 つのトランザクションにまとまった場合もカーソルが同じ文字の位置に残ること、undo/redo でカーソルが戻ること、1 つの undo ステップ内の入力では選択範囲を変換しないこと
- 長いコンテンツの分割（見出しレベル、詰め込み、均等分割、リストを分けない、目次とリンク）と長文の数え方
- オフライン: Service Worker の振り分けとネットワーク優先の応答（キャッシュ失敗・no-store・401）、送信キュー（永続化・順序・恒久的な拒否の判定・同時実行・送信中の追加・削除）、ローカル検索、セッションの「接続不可」状態、サインアウト（サーバーの確認後に端末のデータを削除）、同期後の検索結果の更新
- `hono/jsx/dom` のコンポーネント（Testing Library）: コマンドパレット、検索パレット（開き直すと空から始まる）、一覧（途中のページの失敗と再試行）、エディタ（`?collab=0` でも閲覧者は編集不可）
- テスト用 IdP: 戻り先の制限（同じオリジンのコールバックだけ）、PKCE、パスワードとドメインの制限、コードとトークンの期限・改ざん・取り違え
- サインイン画面: 有効なプロバイダーだけを出すこと、読み込みや開始に失敗したときの表示と再試行
- 設定: デプロイされる `wrangler.jsonc` で開発モードが有効にならないこと、本番の環境にテスト用 IdP がないこと

統合テストの対象:

- テスト用 IdP での OAuth の往復（サインイン、再サインイン、サインアウト）
- マジックリンクと開発用の受信箱がなくなったこと、テスト用 IdP の公開範囲（サインイン画面だけ）
- `TEST_IDP` バインディングがないとき（本番）は、テスト用 IdP のどの入口も開かないこと
- キーセット方式の一覧と件数
- 日本語の全文検索と短い語の部分一致
- 他人のノートへのアクセス拒否（404）、閲覧者と編集者の権限
- 一括投入
- クライアント id でのページ作成が 1 回だけ行われること（再送は 200）と、不正な id・別ノートで使用済みの id の拒否
- WebSocket の認可（未ログインは 401、権限なしは 404、所有者は接続可）と、閲覧者の更新が無視されること
- DO から D1 への書き戻しと、それを全文検索で見つけられること
- JSON 本文が `null` のときに 500 ではなく 400 を返すこと

ブラウザテストの項目:

- UI からのサインイン
- ページ作成と DO への接続
- タグ・WikiLink・スラッシュコマンド
- 別タブに相手のカーソルが表示されること
- 書き戻した本文をパレットの全文検索で見つける
- 無限スクロールでの追加読み込み
- 幅 375px の画面で一覧とエディタが画面幅のほとんどを使えること
- 未共有ユーザーへの 404 と、共有後の閲覧専用表示
- AI ストリーミング（テキスト / Markdown の見出し・リスト・コード・表・引用）
- Service Worker が制御を始めること。オフラインで一覧と開いたことのあるページが開け、サインアウトが無効になること
- オフラインで新しいページを書け、「未同期」として一覧に出て、ローカル検索で見つかること
- オンラインに戻るとページが作成され、ローカル複製のない別ブラウザからも本文が見えること
- サインアウトと、それに伴う API キャッシュ・ページのローカル複製の削除
- ページエラーがないこと
